# Avatar Voice POC

## What this is

A live voice converstaional avatar that let  you type or speak a question,
and the answer is generated by an LLM, grounded in retrieved course content (a small RAG pipeline
over ingested transcripts, via Pinecone), and streamed back as natural-sounding speech in real
time — you hear the answer as it's being generated, not after a full response is ready.

Two ways to try it:

- **Main demo** (`/`) — a text/voice prompt box with an animated speaking orb that reacts to the
  audio as the answer is spoken.
- **Avatar test page** (`/static/avatar.html`) — the same question → grounded answer → speech
  pipeline, but the speech also drives a lip-synced video avatar (via HeyGen LiveAvatar) instead
  of just the orb.

It also remembers the conversation: ask a follow-up question using "it"/"that" and the answer
correctly resolves against what was already asked, within the same browser tab/session.

This is a proof of concept, not a production app — each question is still handled one at a time
(no interrupting the avatar mid-answer), and there's no login/booking/reporting layer yet.

Run + manual-smoke-test instructions below.

## Setup

```
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
```

Copy `.env.example` to `.env` and fill in the keys for whichever features you're using (`OPENAI_API_KEY` is required for everything; the rest are per-feature, see the comments in `.env.example`).

```
uvicorn app.main:app --reload
```

Then open `http://localhost:8000/` for the main orb demo (text/voice prompt in, spoken reply out).

**`.env` changes need a full restart** — `--reload` watches `.py` files, not `.env`; a running process silently keeps its old values otherwise.

## HeyGen LiveAvatar (lip-synced avatar video capability test)

A separate test page, `http://localhost:8000/static/avatar.html`, drives a real-time **HeyGen LiveAvatar** session: your question goes through the same answer pipeline as the main demo (`ANSWER_SOURCE` — `gpt`/`rag`/`agent`), gets spoken by our own TTS (`RealtimeApiSpeaker`), and that audio is pushed to HeyGen so it renders lip-synced video — HeyGen never synthesizes speech itself.

### Env vars

Add to `.env` (see `.env.example` for the full commented block):

```
HEYGEN_API_KEY=<your key>
HEYGEN_API_BASE=https://api.liveavatar.com/v1
HEYGEN_AVATAR_ID=dd73ea75-1218-4ef3-92ce-606d5f7fbc0a   # sandbox "Wayne" avatar, free
HEYGEN_IS_SANDBOX=true
HEYGEN_VIDEO_QUALITY=high
HEYGEN_VIDEO_ENCODING=H264
HEYGEN_SESSION_TIMEOUT_S=30.0
```

Get an API key at [app.liveavatar.com](https://app.liveavatar.com). **Sandbox mode is free** (zero credits) but is locked to the one avatar above, and the API caps sessions at **60 seconds** (`max_session_duration: 60`), measured from session creation — not from when the avatar starts talking. That is enough to verify the pipeline, but **not enough for long answers**: a detailed technical answer can be 40+ seconds of speech, which leaves almost no margin once setup and generation are counted. If the avatar cuts off mid-sentence, this cap is why — see P15 in `architecture-and-query-flow.md`.

**To go live with a real avatar**: pick one in the LiveAvatar dashboard, copy its **UUID**, paste it into `HEYGEN_AVATAR_ID`, and set `HEYGEN_IS_SANDBOX=false`. There is no voice ID to configure — LITE mode (what this integration uses) never lets HeyGen synthesize speech, so the avatar always speaks in whatever voice `RealtimeApiSpeaker` (`REALTIME_VOICE` in `.env`) produces.

**This also matters for session reuse** (added 2026-07-28): one avatar connection now stays open and answers multiple questions in a row without rebuilding the HeyGen session each time (see "Run steps" below). Sandbox's 60-second cap means that reuse only reliably survives a couple of quick back-to-back questions — verified live at 58.22s for two — not a real multi-question conversation with normal think-time between questions. Production billing is **1 credit/min, continuously while the connection is open**, including idle time between questions, not just while the avatar speaks — bounded by the 2-minute idle release described below, not by anything shorter.

### Run steps

1. Add `HEYGEN_API_KEY` to `.env` (see above), then **restart** `uvicorn` (see the `.env`-restart note above).
2. **Verify the HeyGen connection for real first**, before trusting the app: `python -m scripts.check_heygen_session`. This confirms your key/avatar work, that a LITE session actually returns a `ws_url`, and dumps the real event names — read its output if anything below doesn't work.
3. Open `http://localhost:8000/static/avatar.html`.
4. Type a question, press **Ask**. First question: a status line moving through "Starting avatar and thinking…" → "Joining avatar video…" → "Waiting for answer…" → "Avatar speaking…", the avatar's video appears and starts talking in sync with the answer, and the answer text accumulates in the transcript below.
5. Ask a **second** question right after. It should skip straight to "Thinking…" — no "Joining avatar video" step — since the HeyGen session and LiveKit room from question 1 are reused rather than rebuilt. This only actually saves anything with `HEYGEN_IS_SANDBOX=false` (see below); in sandbox mode you'll still see the reuse happen, but the 60s session cap means it can't be relied on for a third question much later.
6. Leave the page idle for 2 minutes (`IDLE_RELEASE_TIMEOUT_S` in `avatar_routes.py`), then ask again: the backend silently releases the HeyGen session and TTS connection after that much inactivity, so this next question rebuilds from scratch (back to step 4's flow) rather than reusing a stale one. This bounds how long a forgotten tab keeps billing.
7. **Stop** closes the whole avatar connection, including the warmed-up session — the next Ask after Stop always rebuilds from scratch. This is a known trade-off, not a bug: Stop cancelling just the in-flight turn while keeping the connection alive would need more work (see `explanation.md` §12).

### Latency

A single WebSocket does the whole turn, and HeyGen session setup runs **concurrently** with answer generation rather than before it — that alone took measured time-to-first-text from ~17.7s down to ~7.8s. See §4 of [`explanation.md`](./explanation.md) for the numbers.

Four different latency numbers get reported, and **they are not interchangeable**:

| Number | Where | What it really means |
|---|---|---|
| `time to first text` | server log / Logfire | question received → first sentence sent to the browser |
| `time to first audio` | server log / Logfire | first PCM byte **leaves OpenAI** — *not* when you hear anything |
| `time to first avatar video` | server log / Logfire | HeyGen confirmed it began rendering |
| **`time to first SOUND`** | **the test page itself** | **the avatar is genuinely audible — the honest number** |

Only the browser can observe the last one, because on this path the browser never receives audio at all (it goes backend→HeyGen). Reading the server-side "first audio" as "when the user hears it" understates reality by roughly 10+ seconds.

Note also that the avatar turn's **total** is not comparable to `/ws/voice`'s: the avatar path waits for the avatar to finish speaking before tearing the session down, while the voice path finishes as soon as the answer is generated and lets the browser play it afterwards.

### Architecture notes

- HeyGen's streaming product is **LiveAvatar** (`api.liveavatar.com`), not the older `api.heygen.com/v1/streaming.*` endpoints or the `@heygen/streaming-avatar` package — those are a previous generation.
- This integration uses **LITE mode**: our audio drives HeyGen's lip-sync, over a plain backend-to-HeyGen WebSocket (`app/services/heygen_streaming.py`). **FULL mode** (HeyGen's own TTS, `avatar.speak_text`) is not used and not implemented — it would need a different transport (the browser publishing to a LiveKit data-channel topic) and would replace our cloned/chosen voice with HeyGen's.
- The browser's only job is rendering the video: it joins the HeyGen-managed LiveKit room **read-only** via `livekit-client` (loaded from a CDN, no bundler) using the `livekit_url`/`livekit_client_token` delivered in the `session` frame over `/ws/avatar`. It never receives `HEYGEN_API_KEY` or the backend's `ws_url` to HeyGen. Once joined it replies `{"type":"ready"}`, and the backend holds the first sentence until then so the avatar never talks into a room nobody has joined.
- No mic input on this page and no HTTPS requirement (`certs/`) — unlike the main demo's voice-input feature, this path only takes typed questions.

### Troubleshooting

- **"HEYGEN_API_KEY is not set in .env"**: add the key and restart uvicorn (see the restart note above).
- **"HeyGen /sessions/start returned no ws_url"**: `scripts/check_heygen_session.py` will reproduce this against the real API — if it also finds no `ws_url`, the backend-driven approach isn't available for your account/mode, and a LiveKit-based fallback would be needed instead (see the integration's design notes in `day-wise-implementation.md`).
- **Video never appears**: check the browser console for a LiveKit connection error. In the Network tab, open the `/ws/avatar` WebSocket's Messages and confirm a `session` frame arrived — if it did and the video is still black, the LiveKit join failed rather than the HeyGen session.
- **No audio/lip-sync**: check server logs for `time to first avatar video` — if it never appears, the turn likely errored before HeyGen's `agent.speak_started` arrived; check the `{"type":"error"}` frame surfaced in the transcript/status line.
- **The avatar stops mid-answer and the video goes black**: almost certainly the 60s sandbox cap, not a bug. Look for `avatar still speaking after 60.0s (X/Y sentences rendered)` in the server log — that is the drain giving up. Ask a shorter question, or move off sandbox.
- **The answer is spoken but the avatar seems to start mid-sentence**: the browser took too long to join LiveKit and the backend gave up waiting after 15s (`browser never confirmed it joined the LiveKit room` in the log). Usually a slow or blocked WebRTC connection.
- **A second question rebuilds the session instead of reusing it**: check the server log for `releasing avatar session after 120.0s with no question` between the two questions — if you see it, more than 2 minutes really did pass (or `IDLE_RELEASE_TIMEOUT_S` was lowered). If you don't see it, check for `avatar turn failed` right before it — a turn error force-releases the session so the next question doesn't retry against a possibly-broken one.
